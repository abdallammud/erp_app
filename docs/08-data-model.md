# Data Model

The entities every module shares, and how they connect. Module-specific entities are detailed on each module's own page; this page is the spine that ties them together.

## Core shared entities

These exist once, at the platform-core level, and every module reads or writes them rather than keeping its own copy.

| Entity | Description | Used directly by |
|---|---|---|
| **Tenant / Organization** | One NGO. Owns everything else — every tenant-scoped table carries a `tenant_id`. See [`02-architecture.md`](02-architecture.md). | All modules |
| **User** | A login. Belongs to exactly one tenant, holds one or more roles. | All modules |
| **Role / Permission** | What a user can see/do; drives which portal(s) they land in. See [`03-roles-and-permissions.md`](03-roles-and-permissions.md). | All modules |
| **Department** | Org unit; used for reporting lines and cost roll-ups. | HRM, Finance |
| **Duty Station / Office** | A physical location the tenant operates from — enables multi-location operation. | HRM, Procurement & Logistics, Programs |
| **Employee** | A staff member — the anchor record for HRM, referenced everywhere staff are assigned to work (projects, requisitions, approvals). | HRM, Finance (cost allocation), Procurement (requisitioner), Programs (project assignment) |
| **Donor** | A funding source. One tenant works with many; one donor may fund many projects. | Finance, Programs, HRM (payroll cost allocation) |
| **Project / Grant** | A funded body of work with a start/end date and a budget envelope. The unit almost everything else ultimately rolls up to. | Finance (cost center), HRM (staff allocation), Procurement (requisition justification), Programs (activities, beneficiaries) |
| **Cost Center / Budget Line** | The specific bucket a cost is charged against within a project's budget. | Finance, HRM (payroll allocation), Procurement (PO budget check) |
| **Vendor / Supplier** | An external party the organization pays for goods/services. | Procurement & Logistics, Finance (Accounts Payable) |
| **Asset** | Any tracked organizational item — laptop to vehicle — with one record regardless of whether it's currently assigned to staff, a warehouse, or a project. | Procurement & Logistics, HRM (staff assignment), Finance (fixed-asset depreciation) |
| **Document / File** | Any uploaded attachment (contract, receipt, ID, safeguarding evidence), stored encrypted with per-record access control. | All modules |
| **Approval Workflow Instance** | A record of a specific approval chain in progress or completed for a specific request (leave, payroll, requisition, etc.). | All modules |
| **Audit Log Entry** | Immutable who/what/when/old-value/new-value record. | All modules |
| **Notification** | An alert generated by the system (approval needed, contract expiring, budget threshold reached, document expiring). | All modules |

## The core spine

Two chains run through the whole system: an **organizational** chain (who works where) and a **funding** chain (who pays for what). Almost every module-specific entity attaches to one or both.

**Organizational chain:**

```
Tenant
  └─ Department / Duty Station / Position
       └─ Employee
            ├─ Payroll & cost allocation
            ├─ Leave & timesheet
            ├─ Performance & training
            ├─ Asset assignment
            └─ Safeguarding cases
```

**Funding chain:**

```
Donor
  └─ Project / Grant
       └─ Cost Center / Budget Line
            ├─ Payroll cost allocation (HRM)
            ├─ Purchase order (Procurement)
            ├─ Distribution (Programs)
            └─ Journal posting (Finance)
```

Where the two chains meet is the single most important design fact in the whole system: **an Employee's time is charged to a Project's Budget Line** via a percentage-allocation on their timesheet/payroll record. That one relationship is what makes donor-compliant cost reporting possible without manual reconciliation — see [HRM → Payroll & Compensation](04-module-hrm.md#c-payroll--compensation) and [Finance → General Ledger](05-module-finance.md#a-general-ledger--chart-of-accounts).

## Data integrity rules

- **Tenant isolation is structural, not optional** — enforced by a global query scope on every tenant-scoped model (see [`02-architecture.md`](02-architecture.md)), not left to individual controllers to remember.
- **Soft deletes everywhere a financial or HR trail matters** — an employee, project, or asset is never hard-deleted while historical transactions reference it; it's archived/deactivated instead, so payroll history and audit trails stay intact.
- **No silent overwrites on financial or approval data** — budget revisions, salary changes, and contract amendments are versioned (old value retained, not replaced), matching the employment-history and profile-change-history pattern established in HRM.
- **Every cross-module money link is a foreign key, not a copied number** — e.g. a payroll run's cost-allocation lines reference the actual Budget Line record; if the budget line's donor code changes, historical payroll reports referencing it reflect that through the relationship, not a stale copy.

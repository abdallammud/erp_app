The core spine

Two chains run through the whole system: an organizational chain (who works where) and a funding chain (who pays for what). Almost every module-specific entity attaches to one or both.

Where the two chains meet is the single most important design fact in the whole system: an Employee's time is charged to a Project's Budget Line via a percentage-allocation on their timesheet/payroll record. That one relationship is what makes donor-compliant cost reporting possible without manual reconciliation — see HRM → Payroll & Compensation and Finance → General Ledger.

Data integrity rules

  • Tenant isolation is structural, not optional — enforced by a global query scope on every tenant-scoped model (see Architecture), not left to individual controllers to remember.
  • Soft deletes everywhere a financial or HR trail matters — an employee, project, or asset is never hard-deleted while historical transactions reference it; it's archived/deactivated instead, so payroll history and audit trails stay intact.
  • No silent overwrites on financial or approval data — budget revisions, salary changes, and contract amendments are versioned (old value retained, not replaced), matching the employment-history and profile-change-history pattern already established in the HRM reference.
  • Every cross-module money link is a foreign key, not a copied number — e.g. a payroll run's cost-allocation lines reference the actual Budget Line record; if the budget line's donor code changes, every historical payroll report referencing it should reflect that through the relationship, not a stale copy.
